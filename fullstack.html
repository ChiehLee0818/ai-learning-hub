01

網路與 HTTP

這是所有東西的地基。前端、後端、資料庫之間發生的每一件事都是 HTTP 請求， 不懂這層，效能問題和安全問題都只能用猜的。

核心觀念
  • 一次請求的生命週期：DNS 查詢（網域換成 IP）→ TCP 連線（三次握手）→ TLS 握手（加密協商，還要多幾趟）→ 送出請求 → 伺服器處理 → 回應 → 連線重用或關閉。每一步都要時間，而且跨國的每一趟都是 0.2 秒起跳。
  • HTTP 訊息的結構：起始行（方法／狀態碼）＋ headers（元資訊）＋ body（內容）。 關鍵在於——header 和 body 是分開送的，可以差很久。
  • 狀態碼分類：2xx 成功、3xx 轉址、4xx 是你（客戶端）錯了、 5xx 是我（伺服器）錯了。看到 5xx 就不要在前端找原因。
  • 快取：瀏覽器快取、CDN 快取各是一層。決定「能不能用舊的」靠 Cache-Control、ETag 這些 header。 而快取的鑰匙是網址——網址一樣，就可能給你舊的東西。
  • TTFB（Time To First Byte）：從送出請求到收到第一個位元組。 它衡量的是「伺服器多久開始回應」，不是「多久回應完」。

你在這個專案碰過的
  • 用 header 找出程式在哪裡執行：x-vercel-id: hkg1::iad1 揭露請求從香港節點進來、但函式跑在美東機房——這是整個效能問題的關鍵線索。
  • 用 header 排除嫌疑犯：x-envoy-upstream-service-time: 7 直接證明資料庫只花 7 毫秒，一口氣排除掉「要不要加索引」這整條路線。
  • 用 curl 拆解一次請求的每個階段：DNS / TCP / TLS / TTFB / 總計 分開量， 看出時間到底卡在連線建立還是資料傳輸。
  • 快取的鑰匙是網址：換照片後沿用同一個檔案路徑，網址沒變， 瀏覽器就一直給舊圖。使用者形容成「儲存後要等很久」—— 其實他沒在等，瀏覽器根本沒去要新的。修法是在網址後面加 ?v={時間戳}。
  • 5xx 的除錯：PDF 匯出連續三次 500，每次原因不同，全部都在伺服器端。
面試可以這樣說 「我用回應 header 來定位效能問題——x-vercel-id 告訴我函式的執行區域， 資料庫回傳的 upstream-service-time 告訴我 DB 只花 7 毫秒。 這兩個免費的線索就把範圍縮到『函式和資料庫之間的網路』。」
還沒碰過的（被問到就這樣答）
  • HTTP/2 與 HTTP/3：多工（一條連線同時跑多個請求）解決了 HTTP/1.1 的隊頭阻塞。平台預設就開了，我沒有自己調過。
  • CORS 跨來源請求：這個專案是同源、加上 Supabase 已設定好，所以沒踩過。但我知道它是瀏覽器的安全機制，靠伺服器回的 Access-Control-Allow-* header 決定。
  • Cookie 的細節屬性（HttpOnly / Secure / SameSite）：由 Supabase 的函式庫代勞，我沒有自己設定過。
  • 速率限制（Rate limiting）：沒做。這是個人專案、流量小，但如果對外開放就必須有。

02

前端基礎：HTML、CSS、TypeScript

框架會換，這三樣不會。而且框架解決不了的問題，最後都會退回到這一層—— 尤其是 CSS，它有一套很多人沒認真學過的規則。

核心觀念
  • 語意化 HTML：用 <button> 而不是可點的 <div>， 因為前者免費得到鍵盤操作、螢幕報讀器支援、正確的預設行為。
  • CSS 特異性（specificity）：不是「寫在後面的贏」，而是一套計分制—— ID > class／屬性／偽類 > 標籤。兩個 class 的選擇器 會贏過一個 class 的選擇器，不管誰寫在後面。
  • 排版：flex（一維）與 grid（二維）＋ gap， 而不是到處補 margin（margin 會塌陷、會互相疊加）。
  • 響應式：相對單位、min() / clamp() 這些現代函式， 很多情況下可以取代媒體查詢。
  • TypeScript 的價值：它在編譯期就告訴你哪裡會壞， 而不是等使用者點到才發現。

你在這個專案碰過的
  • 一個真實的特異性 bug：照片裁切彈窗裡，自己寫的 .crop-modal-img （一個 class）被套件內建的 .ReactCrop__child-wrapper > img （class ＋ 子選擇器 ＋ 標籤，分數更高）蓋掉。結果旋轉成直式的照片沒有高度上限， 把彈窗撐爆、「確定」按鈕被擠出畫面點不到。 修法是疊兩層 class 提高自己的分數。
  • 用型別系統當重構工具：把 color 欄位從型別定義裡拿掉之後， TypeScript 直接把所有還在讀舊欄位的地方標成錯誤—— 不用自己 grep，也不會漏掉角落。這是刻意的手法，不是副作用。
  • 用 min() 避免中等寬度溢出： grid-template-columns: min(720px, 55%) 1fr—— 寫死 720px 會在平板寬度撐破版面，用 min() 一行解決，不用加媒體查詢。
  • stretched-link 版面技巧：卡片要「整張可點」但學名文字要「可以反白複製」。 解法是讓一個透明連結鋪滿整張卡（position:absolute; inset:0）， 文字用 z-index 疊在它上面—— 點空白處導頁、拖曳文字則正常選取。
  • grid 子項的 min-width 陷阱：grid／flex 的子項預設不會縮到比內容小， 所以裡面只要有一個寬表格，就會把整格撐開，外層的 overflow-x 反而攔不住。 要明確設 min-width: 0。
面試可以這樣說 「我踩過一個 CSS 特異性的坑：自己寫的單一 class 樣式被第三方套件的複合選擇器蓋掉， 症狀是彈窗被撐爆、按鈕跑到畫面外。這讓我認真去讀了特異性的計分規則—— 它不是後面的贏，是分數高的贏。」
還沒碰過的
  • Tailwind / CSS-in-JS：這個專案刻意用單一份純 CSS 檔（單人專案，樣式衝突風險低）。我知道 Tailwind 是用工具類別取代自訂 class，取捨是 HTML 變醜但不用煩惱命名和死碼。
  • 設計系統與元件庫：沒有建立可複用的元件庫或 design token 體系。
  • 動畫效能：只知道原則——動 transform / opacity 交給 GPU，動 width / top 會觸發重新排版。沒實際優化過。
  • 系統性的無障礙：有做 aria-label 和鍵盤焦點樣式，但沒有跑過完整稽核工具。

03

React 與元件模型

React 的核心思想只有一句：畫面是狀態的函數。 你改狀態，React 負責更新 DOM。難的不是語法，是「什麼東西該是狀態」。

核心觀念
  • 宣告式 vs 命令式：你描述「畫面該長什麼樣」，不是「怎麼一步步改 DOM」。
  • useState：會觸發重新渲染的資料。 useRef：不會觸發重新渲染的資料（例如拖曳的起始座標）。 選錯會導致每次滑鼠移動都重畫整個元件。
  • useEffect 的正確用途：跟「React 以外的世界」同步 （訂閱事件、操作 DOM API）。如果你用它來「根據 props 算出 state」， 那通常是設計錯了——會多一輪渲染，畫面會閃。
  • useLayoutEffect：跟 useEffect 一樣， 但在瀏覽器繪製之前同步執行。需要「畫面出現前就調整好」的事情要用它。
  • key 的作用：告訴 React「這一項還是原來那一項」。 用陣列索引當 key，在清單重排時會讓狀態黏在錯的項目上。

但這個專案還踩到第二層 框架的 <Link> 導航後會自動捲到頂端，而且執行時機晚於步驟 3—— 會把還原結果整個蓋掉。必須寫 scroll={false} 關掉它。

判斷準則很單純：「使用者不該看到中間狀態」的事情放 useLayoutEffect，其餘一律用 useEffect （因為 useLayoutEffect 會擋住繪製，用多了會拖慢畫面）。

你在這個專案碰過的
  • 為什麼捲動還原要用 useLayoutEffect 而不是 useEffect： 要在瀏覽器畫出畫面之前就把捲軸移到定位， 用 useEffect 的話使用者會看到「先閃到頂端、再跳下去」。
  • 但框架的預設行為會蓋掉你：Next.js 的 <Link> 導航後會自動捲到頂端， 而且執行時機晚於你的 useLayoutEffect—— 所以必須寫 scroll={false} 關掉它。 兩個東西寫同一個值時，順序決定誰贏。
  • 不要用 useEffect 同步衍生狀態：需要「外部參數變了就重設內部狀態」時， 選擇了在 render 期間比對前一次的值，而不是 effect＋setState。理由是 後者會多一輪渲染、使用者可能瞥見舊畫面，而且新版 lint 規則會擋。
  • 用 useRef 存拖曳狀態：照片縮放拖曳時， 起始座標放在 useRef（不需要重繪）， 當前偏移量放在 useState（需要重繪）。
  • Pointer Events 與 setPointerCapture： 自己實作拖曳時，把指標「鎖」在元素上，這樣滑鼠拖出元素範圍也不會中斷。 同一套程式碼同時支援滑鼠和觸控。
面試可以這樣說 「我實作過『從詳細頁返回列表要回到原本捲動位置』。難點不是存位置， 是執行順序——框架的自動捲頂跑在我的還原邏輯之後，會把結果蓋掉。 解法是關掉框架的預設行為，把控制權拿回來。」
還沒碰過的
  • 全域狀態管理（Redux / Zustand / Context）：這個專案的狀態放在網址和元件內就夠了。我知道當「很多層深的元件都要同一份資料」時才需要它，而不是一開始就上。
  • 資料抓取函式庫（React Query / SWR）：處理快取、重試、背景更新、避免重複請求。這個專案是 Server Component 直接抓，沒有這個需求。
  • Suspense 與 Error Boundary：處理「載入中」和「壞掉了」的宣告式邊界。這個專案完全沒有 loading.tsx——而這正好是效能問題的成因之一（見第 04 章）。
  • memo / useMemo / useCallback 的效能優化：有用 useMemo，但沒有真的因為渲染效能問題去調校過。

04

渲染策略：畫面到底在哪裡被產生

這是現代前端面試最常問、也最容易答得含糊的一章。 核心問題只有一個：HTML 是誰產生的、什麼時候產生的。

核心觀念 · 五種策略
策略HTML 何時產生優點代價
CSR
客戶端渲染		瀏覽器下載 JS 之後才畫互動流暢、伺服器負擔小首次白畫面久、SEO 差
SSR
伺服器渲染		每次請求時在伺服器產生首屏快、SEO 好、內容可因人而異每次都要跑伺服器
SSG
靜態產生		建置時就產好最快，直接放 CDN內容不能因人而異
ISR
增量再生		建置時產好，之後定期更新兼顧速度與新鮮度可能拿到稍舊的內容
RSC
伺服器元件		元件層級分別決定細到單一元件的控制邊界看不見，容易誤用
  • Hydration（注水）：伺服器送來的 HTML 是「靜態的圖片」， 瀏覽器下載 JS 之後把事件監聽器接上去，畫面才真的能點—— 這個接電的過程叫 hydration。面試很常問這個詞。
  • Streaming（串流）：伺服器先送 header，再一邊算一邊送 body。 好處是使用者更早看到東西。副作用是——量測時很容易把時間歸錯類。
  • 序列化（serialization）：Client Component 需要的資料必須打包成文字 跟著送到瀏覽器。這是「資料跨越伺服器／客戶端邊界」的真正成本。
  • 動態 vs 靜態路由：只要讀了 cookie 或查詢參數，這個頁面就是「動態」的—— 不能被預先產生、也不能被完整預抓。

中間這 1.4 秒被誤記到前端頭上 於是得出「前端渲染太慢」的錯誤結論，並排了三個打錯目標的方案

串流的設計目的就是盡早把 header 送出去讓瀏覽器開始準備—— 也就是說它會刻意把 header 和 body 的間隔拉大。 這正是為什麼在最多人用的現代框架上，這個量測誤差反而最嚴重。

你在這個專案碰過的
  • Server / Client Component 的判斷標準：預設全部是 Server； 只有需要「記住狀態、處理事件、用瀏覽器專屬 API」時才寫 "use client"。
  • "use client" 標的是「邊界」不是「檔案」： 卡片元件本身沒寫這個指令，但它被 Client Component import， 整包就跟著跨到客戶端。實務建議是把這個指令盡量往下推。
  • 序列化的實際代價：列表頁的互動元件需要全部 313 筆資料當 props， 所以整份資料被打包進回應，壓縮前 211 KB。 對照組是詳細頁——同樣撈了 313 筆，但它是 Server Component，算完就丟，只送 7.8 KB。
  • Streaming 造成的量測陷阱：header 在 0.37 秒就送出，body 卻到 1.8 秒才送完。 用「收到回應」事件當終點，會把 1.4 秒的伺服器時間誤記到前端頭上。（完整案例見第 09 章）
  • 缺少 loading.tsx 的連鎖後果：因為 / 是動態路由， 框架的預設預抓只會抓到「最近的 loading 邊界」為止—— 而這個專案一個都沒有，所以什麼都沒抓。
面試可以這樣說 「我實際量過 Server Component 和 Client Component 的成本差異： 同樣是撈 313 筆資料，Server Component 算完就丟只送 7.8 KB， Client Component 因為要當 props 傳，整份資料被序列化成 211 KB 送到瀏覽器。 這讓我理解到 RSC 的重點不是『在哪裡跑』，而是『資料要不要跨越那條邊界』。」
還沒碰過的
  • SSG / ISR：這個專案所有頁面都是動態（要判斷登入）。如果是部落格或商品頁，SSG＋ISR 會是更好的選擇。
  • Partial Prerendering：把靜態外殼和動態內容混在同一頁的較新做法。
  • Edge Runtime vs Node Runtime：Edge 啟動快、離使用者近，但 API 受限（不能用原生模組）。這個專案的 PDF 匯出就必須用 Node runtime，因為它需要原生二進位檔。

05

後端與 API

後端的工作只有三件：接收請求、驗證與處理、回傳結果。 複雜度來自「跑在什麼樣的機器上」和「怎麼跟前端約定格式」。

核心觀念
  • 兩種伺服器模型： 長駐伺服器（一直開著，有記憶體狀態，可以放連線池和快取） vs Serverless（有請求才啟動、跑完就關、無狀態、按次計費）。 Serverless 的代價是冷啟動和不能保存跨請求的狀態。
  • API 風格：REST（用網址表示資源、用 HTTP 動詞表示操作）、 GraphQL（前端自己描述要什麼欄位，解決過度抓取）、 RPC（直接呼叫遠端函式）。
  • 中介層 middleware：在請求到達真正的處理邏輯之前先攔一手—— 驗證身分、記錄、轉址。集中處理跨路由的共同邏輯。
  • 驗證永遠在伺服器端做。前端驗證只是為了體驗好，不是安全機制。
  • BaaS（Backend as a Service）：把資料庫＋登入＋檔案儲存打包成現成服務， 前端直接呼叫，不用自己寫也不用自己維運後端。

06

資料庫

程式碼壞了可以改，資料壞了通常救不回來。 而且資料庫是唯一一個「你的程式碼不完全控制它」的地方——它有自己的狀態、自己的規則。

核心觀念
  • 約束 constraint：讓資料庫自己擋掉不合法的資料 （非空、唯一、外鍵、check）。放在資料庫的規則沒有人能繞過， 放在程式碼的規則只要有另一個入口就失效。
  • 索引 index：為了避免「整張表掃一遍」。 不同資料型態要用不同索引——一般欄位用 B-tree， 但陣列的「包含」查詢用 B-tree 完全無效，要用 GIN。
  • 交易 transaction：把多個操作綁成一個「全部成功或全部不做」的單位。 只要有一步失敗，前面的都會回復。
  • 遷移 migration：資料庫結構的版本控制。 好的遷移腳本必須能重複執行而不出錯（冪等）。
  • N+1 查詢問題：先查一次拿到 N 筆，再對每一筆各查一次 → 總共 N+1 次往返。 這是最常見的效能殺手，解法是 JOIN 或批次查詢。
  • 正規化 vs 反正規化：前者避免重複儲存，後者為了效能刻意複製一份。
  • 沒有 ORDER BY 就沒有順序保證。回傳順序是未定義的，不保證每次一樣。

你在這個專案碰過的
  • Generated column（自動計算欄位）：屬名不是存進去的， 是資料庫用 split_part(scientific_name, ' ', 1) 自動算的，前端唯讀。 好處是不可能出現「學名改了但屬名忘了改」。
    但它會忠實放大上游的粗心：「有沒有分類」的定義是「學名不是 null」， 如果表單把空欄位送成 "" 而不是 null， 這筆就變成「已分類、但學名是空的」。所以所有選填欄位送出前都要正規化成 null。 "" 和 null 是兩件不同的事。
  • 陣列欄位與 GIN 索引：顏色改成可複選（text[]）時， 原本的 B-tree 索引要換成 GIN——因為 B-tree 對「陣列裡有沒有包含某個值」 這種查詢完全派不上用場。
  • 刻意不加 check constraint：顏色和家族是自由詞彙， 加了約束等於把「使用者可以自由新增」這個功能擋死。 這是有意識的取捨，寫進了文件——不是忘記加。
  • 冪等遷移：整份 schema 檔用 add column if not exists、 drop policy if exists 再 create， 資料回填還加了守衛條件避免重複執行時被套用兩次。全檔 51 處這樣的寫法。
  • Schema 漂移（schema drift）：資料庫裡曾經有一個欄位， 但程式碼和 schema 檔都沒有它——一個被放棄的分支留下的孤兒。 後來建立了明確慣例：還有資料價值的舊欄位保留當備援快照， 作廢功能產生的純複製欄位當場砍掉。
  • 反正規化的實例：「誰新增的」存的是名字的快照而不是關聯 ID。 代價是使用者改名後舊資料還顯示舊名字——這是刻意接受的。
  • 少一個 ORDER BY 的隱形 bug：兩個頁面共用排序邏輯， 但其中一個的查詢漏了排序。結果兩邊資料集合完全相同、只有順序不同， 所以群組數、筆數、總計全部正確，只有「下一張」默默指錯。
面試可以這樣說 「我把一個單值欄位改成陣列時，發現原本的 B-tree 索引對『陣列包含』查詢完全無效， 必須換成 GIN。另外我也刻意不加 check constraint—— 因為那個欄位的產品需求就是要讓使用者自由擴充值域，加了約束等於把功能擋死。 我覺得知道『什麼時候不要用某個技術』跟知道怎麼用一樣重要。」
還沒碰過的（重要缺口）
  • 交易 transaction——而且這個專案有一個真實的後果： 「上傳照片」和「寫入資料列」是兩個獨立操作，不是原子的。 上傳成功但寫入失敗時，Storage 會留下一個沒人指向的孤兒檔案。 當初評估過要不要回滾，結論是不做——因為回滾要在錯誤處理路徑裡再打一次 API， 而那條路徑最可能是網路不通的時候，補救動作同樣會失敗。 這是「知道問題存在、評估後選擇接受」，跟不知道是兩回事。
  • JOIN 與多表關聯：這個專案幾乎是單表，沒有複雜的關聯查詢。
  • N+1 問題：沒遇過，因為採取「一次全撈」的策略——這反而製造了另一種問題（見第 09 章）。
  • 查詢計畫分析（EXPLAIN ANALYZE）：沒用過。資料量太小，索引效果看不出來。
  • 資料庫備份與還原：只有 Supabase 內建的，沒有自己建立備份流程。這是已知的風險，記錄在待辦裡。

07

身分驗證與安全

這一章的每一個錯誤都是真的會出事的錯誤。 而且安全問題的特徵是——它平常不會報錯，出事的時候已經來不及了。

核心觀念
  • 認證 ≠ 授權。認證（authentication）是「你是誰」， 授權（authorization）是「你能做什麼」。兩件事要分開想。
  • 永遠不要信任客戶端送來的東西——包括 cookie。 使用者可以打開開發者工具改掉任何前端的值。
  • 最小權限原則：每一把金鑰、每一個角色，只給剛好夠用的權限。
  • 常見攻擊：XSS（注入惡意腳本）、 CSRF（借用你的登入狀態發請求）、 SQL injection（把指令混進輸入）、 開放式轉址（把轉址參數改成惡意網站）。
  • 秘密管理：金鑰放環境變數不放程式碼。 而且要分清楚哪些金鑰是「可以公開的」、哪些絕對不能外流。

NEXT_PUBLIC_ 這個前綴是很好的設計—— 它把「這個值會被公開」變成你在命名時就必須面對的決定， 而不是等到外流才發現。驗證權限的正確方式也來自這張圖： 要用「繞過前端、直接打資料庫」的方式測試，因為攻擊者就是這樣做的。

你在這個專案碰過的
  • 一個聰明的存取模型設計：需求是「只有我邀請的人能編輯」。 做法不是自己維護一份白名單，而是把公開註冊關掉—— 這樣「已登入」就自動等於「被邀請過的人」， 權限規則只要寫「登入者可以」就夠了。 用設定消除了一整套需要維護的程式碼。
  • RLS（Row Level Security）是真正的權限邊界： 規則寫在資料庫本身，連 API 都繞不過。 前端把按鈕藏起來只是體驗，不是安全。
  • 驗證方式也要繞過前端：拿匿名金鑰直接對資料庫發送新增／修改／刪除， 確認每一種都真的被拒絕——這比在畫面上點一點可靠得多。
  • getUser() vs getSession()： 後者讀的是 cookie 內容（可以被偽造）， 前者會真的拿 token 去問伺服器。凡是「決定能不能做某件事」一律用前者。
    專案有一處用了 getSession()，但那是問「邀請連結有沒有換到 session」—— 本地狀態檢查，不是授權判斷。規則不是「永遠不用」， 是「不要用讀本地資料的方法決定權限」。
  • 開放式轉址防護：登入後要導回原路徑，參數來自網址。 如果不檢查，別人可以構造 ?next=//evil.com 把使用者導去釣魚網站。 防護只有一行：只接受以 / 開頭、但不是 // 開頭的字串。
  • 可公開金鑰 vs 絕對不能外流的金鑰： 這個專案的金鑰帶有 NEXT_PUBLIC_ 前綴—— 這個前綴代表它會被打包進瀏覽器，任何人都看得到。 之所以安全，是因為它的權限完全由 RLS 決定。 而 service role 金鑰會無視所有權限規則， 所以刻意從來沒有放進這個專案。
  • 失效 session 的死結：cookie 還在效期內，前端以為已登入， 但每次查資料都被拒絕，畫面只顯示一句英文錯誤，使用者不可能自己想到要清 cookie。 解法是偵測到「明確被拒絕」時自動清除 cookie。 關鍵細節：只有明確拒絕才算——網路暫時失敗和 5xx 不算， 否則網路抖一下就把所有人登出。
面試可以這樣說 「我設計過一個邀請制的存取模型。關鍵決定是不自己維護白名單—— 而是把公開註冊關掉，讓『已登入』自動等於『被邀請過』， 權限規則就簡化成一條。另外我驗證權限的方式是拿匿名金鑰直接打資料庫， 確認寫入真的被拒絕，而不是只看前端有沒有藏按鈕。」
還沒碰過的
  • OAuth / SSO（用 Google、GitHub 登入）：知道大致流程是「導去第三方 → 拿到授權碼 → 換 token」，但沒實作過。
  • 雙因素驗證：沒做。
  • CSRF token：沒有自己處理，因為靠 SameSite cookie 加上沒有傳統的表單 POST。
  • XSS 防護的細節：React 預設會轉義輸出，所以沒有主動處理過。但我知道 dangerouslySetInnerHTML 會繞過這層保護。
  • 稽核日誌：誰在什麼時候改了什麼，完全沒有記錄。刪除也沒有還原機制——這是已知風險。

08

部署與維運（DevOps）

「在我電腦上會動」是工程師最著名的一句藉口。這一章就是在講 為什麼本機和正式環境永遠不一樣，以及怎麼縮小那個差距。

核心觀念
  • 環境分離：開發 / 預覽 / 正式，各自有獨立的設定和資料。
  • 環境變數與秘密：設定不寫死在程式碼裡。 而且要分清楚哪些變數會被打包進前端（那就等於公開）。
  • CI / CD：CI 是「每次提交自動檢查」（跑測試、跑 lint）， CD 是「檢查過就自動部署」。
  • CDN 與邊緣節點：靜態內容放在離使用者近的地方。 但注意——邊緣節點通常只是入口，真正跑程式的地方可能在很遠的機房。
  • 區域選擇與資料重力：運算應該靠近資料。 資料通常比程式碼重，搬運資料的成本遠大於搬運運算。
  • 觀測性：logs（發生了什麼）、metrics（數字趨勢）、traces（一次請求走過哪些環節）。

09

效能：先量，再改

效能工作有一條鐵律：不量就是猜。 而這一章最重要的教訓是——量錯了比不量更危險， 因為錯誤的量測不會給你「沒有答案」，它會給你一個看起來很合理的錯答案。

核心觀念
  • 先找瓶頸，再優化。優化一個佔總時間 2% 的環節， 就算做到完美也只快 2%。
  • 控制變因：一次只改一個條件，用對照組排除嫌疑犯。 這是除錯真正的核心技巧，不是效能專屬的。
  • Core Web Vitals：Google 定義的三個使用者體感指標—— LCP（最大內容多久畫出來）、 INP（點下去多久有反應）、 CLS（畫面有沒有亂跳）。
  • 快取有很多層：瀏覽器、CDN、伺服器、資料庫， 每一層都可能給你舊資料。快取是最容易引入 bug 的優化手段。
  • 前端的常見瓶頸：JS 檔太大、圖片沒優化、一次渲染太多元素、主執行緒被長任務卡住。
案例研究 · 「返回列表很慢」的完整除錯過程

症狀

使用者說：「從詳細頁按返回列表，等待時間太久。」 一句沒有數字的抱怨——所有效能問題的起點。

第一次診斷：錯的

第一輪測法是監聽自動化工具的「收到回應」事件，當作伺服器工作的結束時間； 再看卡片何時出現，中間的差當作前端渲染時間。結論是 「伺服器 0.35 秒很快，前端渲染 1.4–1.8 秒是兇手」， 並排了三個方案：收合群組、分頁、虛擬化。

三個方案全部打錯目標，因為那個事件是 header 一到就觸發，而框架用的是 streaming—— header 先送、body 邊算邊送。1.4 秒的伺服器時間被整段記到前端頭上。

  • 所有時間點用同一個時鐘——全部在瀏覽器內部取，測試腳本只當信差不當碼表
  • 用能分辨 header 和 body 的工具——Resource Timing API 的 responseStart（header 到）對 responseEnd（body 到齊）

10

測試

這是這份地圖上最薄的一章，要誠實承認。 但「知道自己缺什麼、也知道該怎麼補」，比假裝有經驗好得多。

核心觀念
  • 測試金字塔：單元測試（測單一函式，快、多）、 整合測試（測幾個模組串起來）、 E2E 測試（模擬真人走完整流程，慢、少但最接近真實）。 底層要多、頂層要少，因為越上層越慢越脆弱。
  • 為什麼需要測試：不是為了證明「現在是對的」， 而是為了下次改動時知道有沒有弄壞別的東西（迴歸）。
  • 測試替身（mock / stub）：把外部依賴（資料庫、API）換成假的， 讓測試快且可重複。
  • 純函式最好測：同樣輸入永遠同樣輸出、沒有副作用。 這也是為什麼「把邏輯抽成純函式」是好的設計。

倒過來了。只有最貴、最慢的那一層有東西， 而且沒有 CI，每次都要人工在本機跑。

最該補的第一塊 那個共用的篩選／排序／分組邏輯是純函式——給定資料和參數、回傳排好的清單， 沒有資料庫、沒有畫面、沒有副作用。
它是全專案最好測的地方，而且它真的出過一次「所有數字都對、只有順序悄悄錯了」的 bug—— 正是單元測試最擅長抓的類型。

金字塔的重點不是「E2E 不好」，而是比例。 E2E 能證明「整條路是通的」，但它跑一次要好幾秒、環境一抖就假性失敗、 壞掉時你只知道「某個地方壞了」。單元測試會直接告訴你是哪一行。

你在這個專案碰過的
  • 用 Playwright 做 E2E 驗證：以訪客身分走過流程， 確認未登入看不到編輯按鈕、受保護路由會被導向登入頁、 篩選條件在返回後有保留。
  • 對照資料庫驗收，而不是只看畫面：分組筆數對不對， 是拿畫面上的數字跟直接查資料庫的結果比對的。
  • 測試工具會製造它自己的假象：整頁截圖看起來圖片全沒載入， 實際上是 loading="lazy" 還沒被觸發—— 截圖是「把視窗撐到全頁高度後瞬間拍照」，下面的圖根本沒機會載入。 正確做法是捲到定位後檢查圖片的實際寬度。
  • 量測方法本身要先被驗證：這是第 09 章最大的教訓—— 你的測試工具可能正在對你說謊。
面試可以這樣說（誠實版） 「這個專案沒有自動化測試套件，這是我明確知道的缺口。 我做的是用 Playwright 手動寫腳本做關鍵路徑的驗證和效能量測。 過程中我學到一件事——測試工具本身會製造假象， 我遇過整頁截圖看起來圖片全沒載入，其實是延遲載入還沒觸發。 如果要補，我會從純函式的單元測試開始，因為那部分邏輯最集中也最好測。」
還沒碰過的（這一章幾乎全是缺口）
  • 單元測試框架（Jest / Vitest）：專案裡沒有任何測試檔，package.json 也沒有 test 指令。
  • 測試覆蓋率：沒量過。
  • CI 上自動跑測試：沒有流水線，每次都是手動在本機跑 build 和 lint。
  • TDD：沒有實踐過。
  • 最該補的第一步：那個共用的篩選／排序／分組邏輯是純函式—— 給定資料和參數，回傳排好的清單。這是全專案最適合寫單元測試的地方， 而且它出過一次「順序悄悄錯掉」的 bug，正是單元測試最能抓到的類型。

架構決策與技術債

資深和資淺的差別通常不在「會不會寫」，而在 「知不知道自己在做取捨」以及「有沒有把取捨記下來」。

核心觀念
  • 狀態該住在哪裡：元件內、網址、瀏覽器儲存、伺服器—— 問兩個問題就能決定：「它要活多久？」「別人需要看到它嗎？」
  • 單一真相來源：同一件事不要有兩份答案。 兩份遲早會不一致，而且不一致的時候通常沒有人會發現。
  • 技術債不等於爛程式碼：多數技術債是 「當初正確的判斷，但前提條件變了」。
  • 把決策的理由寫下來：尤其是「我們刻意不做 X」—— 因為下一個人（包括三個月後的你）看到缺少 X，會以為是忘了做。

PWA：讓網站變成手機上的 App

使用者說「我想在手機上像 App 一樣用」的時候，直覺反應通常是「那要再寫一套 App 嗎」。 答案是不用——同一個網站，加一份說明檔和幾張圖示，手機就會願意把它當 App 對待。 這一章是關於那份說明檔裡寫了什麼，以及它做不到什麼。

核心觀念
  • 網站與原生 App 的差別：原生 App 是下載到手機裡的一包程式，有自己的圖示和視窗、可以離線， 代價是要送審、更新要再送一次、使用者得去商店安裝。網站改完就生效， 但它永遠長得像網頁——有網址列、要先打開瀏覽器才找得到。
  • PWA 是中間那條路：Progressive Web App。 骨子裡還是同一個網站，一行功能都沒改， 只是多放了一份檔案告訴手機「我希望被當成 App 對待」。
  • Web App Manifest：那份檔案就是它，一份 JSON，寫著名稱、圖示、主題色。 關鍵的是 display: "standalone"——這一行是在說 「從主畫面開啟時不要顯示網址列與工具列」。 少了它，「加到主畫面」就只是一個開在瀏覽器裡的書籤。
  • 「可安裝」和「可離線」是兩件事：manifest 只負責前者。 離線要另外寫 Service Worker——一段跑在瀏覽器背景、 能攔截網路請求並回傳快取內容的程式。 沒有它，PWA 看起來像 App，但沒網路就打不開。
  • 平台差異是真的會咬人的地方： iOS 完全不讀 manifest 裡的 icons，只認 apple-touch-icon， 所以必須另外放一張；Android 則會把圖示裁成圓形／方形／水滴形（看廠牌）， 圖案得縮在中央、四周留安全區，這種圖叫 maskable。
  • 安裝的前提是 HTTPS。這不是額外的工作，而是現代部署平台的預設值， 但它是條件之一——純 HTTP 的站不會被當成可安裝的 App。

這張圖的重點是右邊那一欄。PWA 最容易被誤解的地方， 是把「看起來像 App」當成「就是 App」—— 安裝了不等於能離線，這兩件事在技術上完全分開。

你在這個專案碰過的
  • 用框架的檔案慣例產生 manifest：放一個 manifest.ts 在指定位置， 框架會自動輸出 /manifest.webmanifest 並在 <head> 插入對應的 <link>。不需要自己寫那個標籤，但要知道它被產生了—— 驗證時看的就是它在不在。
  • 四張圖示，分別給不同平台：192／512 給 Android，512 的 maskable 版本 另外做（把圖縮到畫布中央約 75%、四周補底色當安全區，不然邊緣會被裁掉）， 再加一張 180×180 的 apple-icon 給 iOS。 iOS 那張不能省——它不讀 manifest 裡的 icons。
  • 踩到框架版本差異：主題色設定在這個版本已經從 metadata 搬到獨立的 viewport 匯出。 寫在舊位置不會報錯，只是被安靜忽略—— 這類「沒有錯誤訊息的失效」最難發現，只能靠實際檢查產生出來的標籤。
  • 背景色要跟站上的底色一致：那是啟動時的過場顏色， 設錯會在開啟瞬間閃一下白畫面。
  • iOS 主畫面的 PWA 有自己的快取，跟 Safari 分開， 而且沒有網址列也就沒有重新整理鈕。 正式站更新後手機還看到舊畫面時，唯一的解法是把圖示刪掉重加一次—— 實際踩過，第一次遇到會以為是部署失敗。
  • 圖示「消失」過一次，原因不在圖示：那批檔案當時只存在於某個分支上， 主線根本沒有。症狀出現在手機上，原因在版本控制， 查錯方向差了十萬八千里。
面試可以這樣說 「使用者希望手機上能像 App 一樣用。我沒有另外寫原生 App， 而是加了 PWA 支援——一份 manifest 加四張圖示， 關鍵是 display: standalone，它讓網站從主畫面開啟時不顯示網址列。 過程中學到兩件事：一是平台差異必須個別處理， iOS 不讀 manifest 的圖示、Android 會把圖示裁成不同形狀； 二是『可安裝』和『可離線』是分開的， 我這個專案只做了前者，沒有 Service Worker，所以沒網路就打不開。 這是我明確知道的邊界，不是以為做完了。」
還沒碰過的
  • Service Worker：站上沒有（/sw.js 回 404，查證過）。 所以沒有離線瀏覽、沒有快取策略、沒有背景同步。 這是這一章最大的缺口，也是「像 App」和「是 App」之間真正的距離。
  • 快取策略：cache-first／network-first／stale-while-revalidate 這些取捨， 知道名字但沒有實作過。對這個專案還特別敏感—— 照片是主要內容，快取策略下錯會直接影響流量帳單（見第 09 章）。
  • 推播通知（Web Push）：沒做，這個專案也沒有需要通知的場景。
  • 安裝提示（beforeinstallprompt）：沒有做引導安裝的自訂 UI，靠使用者自己從瀏覽器選單加入。
  • Lighthouse 的 PWA 稽核：沒跑過。 驗證方式是自己一項項確認產生出來的標籤和檔案， 能確認「有沒有」，但沒有一份標準化的評分。

面試官問「講一個你解決過的難題」，他要聽的不是你多會寫程式， 而是你怎麼在資訊不足的情況下逼近答案。

第 2 步和第 3 步才是這個故事真正的價值 「我找到並修好了一個 bug」是每個人都會講的。
「我發現我們原本的判斷是錯的，而且我說得出為什麼會錯」——這個層次的人少很多。

面試時不要跳過第 2 步。承認第一版是錯的不會扣分， 反而證明你有能力質疑既有結論、也有能力驗證自己。

主線故事（STAR 格式）

Situation

我維運一個自己的圖鑑網站，前端 Next.js、資料庫 Supabase、部署在 Vercel。 使用者回報「從詳細頁返回列表要等 1 到 2 秒」。

Task

第一版診斷認為是前端一次渲染 313 張卡片太重，排了三個方案。 但我在動工前想先確認方向對不對，所以重新量了一次。

Action

我先發現舊量測方法有瑕疵：它用「收到回應」事件當伺服器結束時間， 但那個事件是 header 一到就觸發，而框架是串流回應——header 先送、body 邊算邊送。 所以一大段伺服器時間被誤算成前端時間。

改用 Resource Timing API 分辨 header 和 body 的抵達時間、把所有觀測放在同一個時鐘上， 再加 Long Task API 確認主執行緒有沒有真的被卡住。 結果前端渲染只有 33 毫秒、長任務 0 個——原本的方向是錯的。

接著設計對照組縮小範圍：比較有查資料庫和沒查的頁面、 比較送 7 KB 和送 214 KB 的頁面、比較同一份程式碼跑在正式站和本機。 三組對照分別排除掉資料量、渲染量、程式碼本身。

最後從回應 header 找到答案：函式跑在美東機房，而資料庫回報自己只花 7 毫秒—— 99% 的時間花在兩者之間的網路距離上。

Result

根因確認後方案完全換了一批，最高投報率的是把函式區域搬到跟資料庫同一區， 零程式碼改動、而且列表頁和詳細頁會一起變快。 最大的收穫是：錯誤的量測不會給你「沒有答案」， 它會給你一個看起來很合理的錯答案。

被追問時的答法

你怎麼確定不是資料庫慢？

資料庫每個回應都夾帶它自己的處理時間，全欄 313 筆是 7 毫秒。

另外有旁證：同一份程式碼跑在本機時整頁 0.28 秒就完成，代表拿資料本身不是問題。

為什麼不直接加快取？

可以，但要先想代價：使用者的典型流程是編輯完一筆就返回列表。 如果快取沒正確失效，他會看到自己剛改的東西沒更新——那比慢 1 秒更糟。

相較之下「把伺服器搬到資料庫旁邊」沒有正確性風險，所以排在前面。 快取是最容易引入 bug 的優化手段，通常該是最後一招而不是第一招。

如果是團隊專案，你會怎麼避免同樣的事？

兩件事。第一，紀錄要寫量測方法不只寫結論—— 這次錯誤能被抓出來，就是因為舊紀錄有寫「怎麼量的」。

第二，動工前先確認「這個修法會影響總時間的百分之幾」。 舊方案要優化的部分只佔 2%，就算做到完美也只快 2%。 這個檢查五分鐘，可以省下好幾週。

你們有寫測試嗎？

照實說：沒有自動化測試套件，這是我知道的缺口。 我用 Playwright 寫過關鍵路徑的驗證腳本，但沒有 CI 流水線。

如果要補，我會從那個共用的篩選排序邏輯開始——它是純函式，最好測， 而且它真的出過一次「所有數字都對、只有順序悄悄錯了」的 bug， 正是單元測試最能抓到的類型。

你自己寫了多少程式？

照實回答。如果你的角色偏產品／規劃，就說你負責定義問題、 驗證方向、決定優先順序，實作由誰完成。

誠實反而加分——「發現方向錯了並把它擋下來」本身就是資深判斷， 不需要靠誇大實作份量來包裝。面試官最怕的是講不出細節的人，而這些細節你全都有。

三個可以帶到任何專案的原則

一、先量再改

優化一個佔 2% 的環節，做到完美也只快 2%。而且量錯比不量更危險。

二、挑一個不會說謊的觀測點

畫面文字可以由很多原因造成，但「網路請求有沒有發出去」只有一個解釋。 「刪除有沒有成功」不要看有沒有報錯，要看實際影響筆數。

三、預設值也是一種決定

這次的兩個根因——伺服器在美東、沒有預抓—— 都不是有人選錯，是沒有人意識到這裡有一個選擇。 除錯時「這裡的預設值是什麼、為什麼」永遠值得問一次。
