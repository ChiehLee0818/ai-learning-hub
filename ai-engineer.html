FastAPI：一個最小 AI endpoint
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class AgentRequest(BaseModel):
    message: str
    thread_id: str

class AgentResponse(BaseModel):
    answer: str

@app.post("/agents/run", response_model=AgentResponse)
async def run_agent(req: AgentRequest):
    if not req.message.strip():
        raise HTTPException(status_code=400, detail="message is empty")

    # 真實系統會在這裡 load state → invoke agent → persist result
    answer = f"Received: {req.message}"
    return AgentResponse(answer=answer)
  • Path parameter：/users/{user_id}
  • Query parameter：?limit=20&offset=0
  • Header：Authorization、Content-Type、trace ID
  • Body：通常 JSON
  • 401 vs 403：沒有有效身份 vs 有身份但沒有權限
  • 429：rate limit；5xx：server-side failure
  • Idempotency：重送 request 不應重複扣款 / 重複改機台參數

1.3 SQL：你要真的會寫的範圍

建立最小 conversation schema
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE conversations (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    title TEXT,
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE messages (
    id BIGSERIAL PRIMARY KEY,
    conversation_id BIGINT NOT NULL REFERENCES conversations(id),
    role TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'tool')),
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
);
JOIN + GROUP BY：每個 user 有多少訊息？
SELECT
    u.id,
    u.email,
    COUNT(m.id) AS message_count
FROM users u
LEFT JOIN conversations c ON c.user_id = u.id
LEFT JOIN messages m ON m.conversation_id = c.id
GROUP BY u.id, u.email
ORDER BY message_count DESC;

至少要熟：SELECT / WHERE / JOIN / GROUP BY / HAVING / ORDER BY / INSERT / UPDATE / DELETE，再加上 subquery、CTE、transaction 的概念。

1.5 Index：為什麼快？又為什麼不能亂加？

沒有合適 index，DB 可能需要掃大量 rows；B-tree index 讓它可快速縮小搜尋範圍。但 index 也要佔空間，而且每次 INSERT / UPDATE / DELETE 都要維護。

Composite index + EXPLAIN ANALYZE
CREATE INDEX idx_messages_conversation_created
ON messages (conversation_id, created_at DESC);

EXPLAIN ANALYZE
SELECT *
FROM messages
WHERE conversation_id = 123
ORDER BY created_at DESC
LIMIT 20;
Composite index 順序很重要：(conversation_id, created_at) 不等於所有查詢都能有效用到 (created_at, conversation_id)。

1.6 Transaction / ACID

兩個更新要一起成功或一起失敗
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- 任一步失敗 → ROLLBACK
AAtomicity一組操作全成或全敗
CConsistencyconstraint / invariant 前後仍成立
IIsolation同時交易不要互相看到不合理中間狀態
DDurabilitycommit 後，即使 crash 也不該消失

PostgreSQL 用 MVCC 維護多個 row version，讓不同 transaction 看到符合隔離規則的 snapshot；一般讀寫因此可以減少互相阻塞。

↔

1.10 Redis：為什麼 Agent 系統常看到它？

Cache-aside pattern
def get_product(product_id):
    key = f"product:{product_id}"

    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    product = db.query_product(product_id)
    redis.setex(key, 300, json.dumps(product))  # TTL 5 min

常見用途：cache、session、短期 state、rate limiting、distributed lock、queue / pub-sub。陷阱：cache invalidation、stale data、TTL、memory pressure。

Q：PostgreSQL、Redis、MongoDB 都能存 JSON，那為什麼不全部選一個？

因為產品選擇不是只看「能不能存」。要看 transaction / relation / query pattern / latency / consistency / scale。Postgres 適合主業務資料；Redis 適合快速、暫時性的 key-based data；MongoDB 適合自然以 document 聚合且 schema 常變的資料。

2. Vector Database Fundamentals

RAG 要學深，不能只停在「把 embedding 丟進 vector DB」。你至少要知道它如何找鄰居、index 為什麼是 approximate，以及 metadata filter 怎麼跟 vector search 配合。

2.1 Embedding 到底存什麼？

"packing pressure too low"
→ Embedding Model →
[0.12, -0.44, 0.08, ...]
→
Vector Index

2.2 Cosine、Dot Product、Euclidean

Metric直覺注意
Cosine similarity比較方向是否相近常用於 normalized embeddings
Dot product方向 + magnitude模型定義會影響適用性
Euclidean (L2)空間距離依 embedding model / index 支援選用

2.3 Exact Search vs ANN

Exact

query 對所有 vectors 算距離。

準，但資料大時慢。

ANN

Approximate Nearest Neighbor：用 index 快速找很可能最近的候選。

用少量 recall 犧牲換 latency。

2.4 HNSW：面試要懂到哪？

把 HNSW 想成多層近鄰導航圖：上層節點少，大步跳到大致區域；逐層往下，在更密的圖裡找附近鄰居。

Layer 2：少量節點 → 大步導航
Layer 1：更多節點 → 縮小範圍
Layer 0：最密 → 找近鄰

不需要手寫 HNSW，但要會說 index build / memory 成本較高，query recall 與 speed 可透過搜尋參數取捨。

2.5 IVF：另一種直覺

先把 vectors 分群；query 時先找相關 cluster，再只掃這些 cluster。掃得越多，recall 通常越高，但越慢。

2.6 pgvector：Postgres 也可以做 Vector Search

概念 SQL：vector column + HNSW index
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    metadata JSONB,
    embedding VECTOR(1536)
);

CREATE INDEX ON documents
USING hnsw (embedding vector_cosine_ops);

SELECT
    id,
    content,
    1 - (embedding <=> :query_embedding) AS cosine_similarity
FROM documents
WHERE metadata->>'product' = 'A'
ORDER BY embedding <=> :query_embedding
LIMIT 5;

2.7 Dedicated Vector DB vs pgvector

情境pgvector 常很合理Dedicated Vector DB 可能更合理

資料關係embedding 和 relational metadata 緊密向量規模 / throughput 很大
團隊維運團隊熟 Postgres需要專門 distributed vector features

PHASE 1 · MODULE 3

3. RAG 深度知識

你要從「知道 RAG 流程」提升到「能找出 retrieval、ranking、context、generation 到底哪裡壞掉」。

1.1 RAG 的完整資料流

離線：文件 → 清理 → Chunking → Embedding → Index / Vector DB
線上：Query → Query Rewrite → Retrieval → Filter → Rerank → Context Build → LLM → Citation / Validation
評估：Retrieval Recall → Ranking → Context Quality → Faithfulness → Answer Quality

1.2 Chunking：不是越小越好

策略優點缺點適合
固定 token簡單、穩定容易切斷語意結構普通、快速 baseline
Recursive / paragraph保留語意大小較不一致大多數文件
Semantic chunking語意完整成本高、參數敏感高價值知識庫
Parent-child小塊找得準，大塊給上下文索引與 serving 較複雜長文件、policy、manual
面試重點：chunk size 是 recall 與 context precision 的 trade-off。太小：語意破碎；太大：embedding 稀釋、context 塞雜訊。

1.3 Dense、Sparse、Hybrid Search

Dense

用 embedding 找「語意相近」。

強：同義詞、自然語言。弱：精準代碼、料號、罕見詞。

Sparse / BM25

用詞頻與關鍵字匹配。

強：產品型號、錯誤碼、專有名詞。弱：語意改寫。

Hybrid

Dense + Sparse 再融合排序。

企業知識庫常比單一方法穩。

你要知道的融合方式

Weighted Score：把 dense / BM25 分數正規化後加權。
RRF（Reciprocal Rank Fusion）：不依賴不同系統分數尺度，只看排名，常比較穩。

1.4 Retrieval、Reranking 是兩件事

Query
→
Retriever
快，取 Top-50
→
Reranker
慢但準，排成 Top-5
→
LLM Context

Retriever主要追求 recall；Reranker主要追求 precision。Cross-encoder reranker 通常比 embedding cosine 更能理解 query-document 關係，但成本較高。

1.5 Query Transformation

方法在解什麼問題風險
Query Rewrite原問題太口語、缺上下文改壞原意
Multi-query一種說法找不到資料成本與噪音增加
HyDEQuery 太短，embedding 不夠好假設性文件可能導偏
Decomposition複合問題需拆多步流程變慢、錯誤會傳遞

1.6 Metadata Filtering

除了「語意」，企業 RAG 常必須先限制：部門、產品、版本、日期、權限、文件類型。這能大幅降低 search space，也能避免拿到不該看的資料。

陷阱：不要把 access control 只交給 prompt。「請不要顯示機密文件」不是安全機制；權限應在 retrieval / data access 層強制。

1.7 RAG Failure Taxonomy：錯誤分類

層症狀檢查方式可能修法
Query問題模糊、代名詞太多看 rewrite 前後clarification / rewrite
Retrieval正確文件沒進 Top-KRecall@Khybrid、chunk、embedding
Ranking找得到但排序差MRR / NDCGreranker
Context正確資訊被雜訊淹沒context precision縮小、去重、壓縮
Generationcontext 有答案卻答錯faithfulness / manual inspectprompt、model、structured output

1.8 重要 Retrieval Metrics

Recall@K

相關文件有沒有被找進前 K 筆？

找到的 relevant / 全部 relevant

Precision@K

前 K 筆裡有多少真的 relevant？

relevant in top K / K

MRR

第一個正確答案排多前面？

適合「一個正確答案」型搜尋。

NDCG

考慮多個結果的相關程度與排名。

適合 relevance 有高低等級。

1.9 GraphRAG 與 Agentic RAG

GraphRAG

當問題依賴實體關係與多跳關聯時，把 entity / relation 建成 graph，再做 traversal / community summary。

不是「RAG 加一張圖」；價值在於跨文件關係與 global question。

Agentic RAG

讓 agent 決定要不要搜、搜哪裡、要不要改 query、是否多輪 retrieval。

更彈性，但也更慢、更難評估、更不 deterministic。

3.10 Code：一條可 debug 的 RAG pipeline

不要把 retrieval、rerank、generation 全包成一個黑盒。拆開後 production 答錯才知道錯在哪。

Python：retrieve / rerank / generate 分層
def answer(query: str):
    rewritten = rewrite_query(query)

    candidates = retriever.search(
        rewritten,
        k=50,
        filters={"product": "A"},
    )

    ranked = reranker.rank(query, candidates)
    context = ranked[:5]

    response = llm.invoke({
        "question": query,
        "context": context,
        "instruction": "Answer only from context; cite evidence."
    })

    return {
        "answer": response,
        "retrieved_ids": [x.id for x in candidates],
        "context_ids": [x.id for x in context],
    }

3.11 LangChain：把 retrieval 包成 Agent Tool

目前 LangChain 高階 agent API 是 create_agent。如果 RAG 是可選能力，可包成 tool；若流程一定要先 retrieve，deterministic workflow 通常更合理。

LangChain create_agent + retrieval tool（簡化）
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def search_knowledge_base(query: str) -> str:
    """Search internal manufacturing knowledge."""
    docs = retriever.search(query, k=5)
    return "\\n\\n".join(
        f"[{d.id}] {d.text}" for d in docs
    )

agent = create_agent(
    model="openai:YOUR_MODEL",
    tools=[search_knowledge_base],
    system_prompt=(
        "Use the knowledge-base tool for factual manufacturing questions. "
        "Cite document IDs and do not invent unavailable evidence."
    ),
)

result = agent.invoke({
    "messages": [
        {"role": "user", "content": "Why can low packing pressure cause shrinkage?"}
    ]
})
API 方向參考：LangChain Agents
Q：RAG 回答錯了，你怎麼 debug？

好回答框架：先分層，不直接換模型。確認 query 是否清楚 → gold evidence 有沒有被 retriever 找到 → reranker 是否把它排前面 → context 是否含正確內容且沒有互相衝突 → LLM 是否 faithful。每層用對應 metric 與 trace 證明。

追問：如果 Recall@10 很高但答案還是錯？

那問題多半不是 retrieval recall，而可能是 ranking、context clutter、prompt grounding 或 generation；再檢查正確 chunk 排名、context precision 與 faithfulness。

工具定義要清楚：名稱、用途、參數 schema、限制、錯誤回傳。LLM 只負責選擇與填參數，真正權限與商業規則仍應由 backend enforcement。

2.5 State 與 Memory 不一樣

State

這一次 workflow 執行中的必要資訊。

例：目前步驟、tool result、retry count、user intent。

Memory

跨 turn / 跨 session 想保留的資訊。

例：使用者偏好、長期任務上下文。

記憶不是越多越好。長期 memory 要考慮 relevance、過期、衝突、隱私與是否真的值得寫入。

2.6 Multi-Agent：什麼時候值得？

適合：不同 agent 有明確不同工具 / 權限 / domain、可平行處理、或需要 ownership boundary。

不適合：只是把一條 chain 拆成很多「角色」，結果多了協調成本，卻沒有能力邊界。

2.7 Determinism 與 Guardrails

Agent 越自由，越要把「不能錯」的部分從 LLM 移出去。

LLM 適合：理解、分類、生成、候選方案
程式控制：schema、workflow transition、retry limit、timeout、business rules
安全控制：RBAC、approval、sandbox、audit log

2.8 Termination：怎麼避免 Agent 無限跑？

常見停止條件：任務完成、達最大 step、達 token / cost budget、工具連續失敗、confidence 不足轉人工、偵測循環。

層級現在適合用什麼你控制什麼

3.2 Self-Attention：淺白版

每個 token 都會問：「在理解我時，我現在應該看句子裡哪些 token？」

Q我正在找什麼？
K我有什麼特徵可以被別人找到？
V如果別人關注我，我要提供什麼內容？

核心計算可理解成：Attention(Q,K,V) = softmax(QKᵀ / √d) V。你不一定要手算，但要知道 QK 決定「看誰」，V 決定「拿什麼資訊」。

3.3 Multi-Head Attention

不同 head 可以同時學不同關係，例如語法依賴、指代、位置或語意關係。最後再合併。

3.4 Position：Transformer 怎麼知道順序？

純 attention 本身不懂 token 順序，所以需要 positional information。現代 LLM 常見 RoPE 類方法，將相對位置信息帶進 attention。

3.5 Context Window 與 Lost in the Middle

Context window 是模型單次能處理的 token 範圍，但塞得下 ≠ 用得好。上下文太長會增加 latency / cost，也可能讓重要資訊被雜訊稀釋；模型對中間資訊的利用有時也較弱。

3.6 KV Cache

自回歸生成時，前面 token 的 Key / Value 不需要每生成一個 token 都重新算。把它們 cache 起來，就能加快 inference。

Trade-off：速度換記憶體。Context 越長、batch 越大，KV cache 佔用越高。

3.7 Temperature / Top-k / Top-p

參數意思直覺
Temperature調整 logits 分布尖銳程度低：穩定；高：多樣
Top-k只從機率最高的 k 個 token 選硬切候選數
Top-p選到累積機率達 p 的候選集合候選數會動態變

3.8 SFT、RLHF、DPO

方法做什麼
Pretraining大量資料學一般語言與知識
SFT用 input-output 範例教模型遵循任務
RLHF透過人類偏好與 reward model 進一步對齊
DPO直接用 preferred / rejected pairs 做偏好最佳化，流程較簡化

3.10 LoRA、Quantization、MoE

LoRA

凍結原權重，只訓練低秩 adapter，降低 fine-tuning 成本。

Quantization

降低權重 / activation 精度，省記憶體、加速，但可能掉準確率。

MoE

很多 expert，但每個 token 只啟用部分 expert；擴大模型容量又控制計算量。

5.11 Code：Self-Attention 其實就是「算分數 → softmax → 加權 V」

這是概念版，不是 production Transformer 實作；目的是讓你面試時真的知道公式每一步在做什麼。

NumPy 風格概念 code
import numpy as np

# shape: [num_tokens, head_dim]
Q = ...
K = ...
V = ...

d = Q.shape[-1]

# 1. 每個 token 對其他 token 的相關分數
scores = (Q @ K.T) / np.sqrt(d)

# 2. 轉成 attention weights
weights = softmax(scores, axis=-1)

# 3. 用 weights 對 V 做加權平均
output = weights @ V

記法：QKᵀ 決定「看誰」；V 決定「從那個 token 取什麼資訊」。

5.12 Code：Temperature 改的是機率分布，不是「讓模型突然會創意」

Sampling 概念
def probabilities(logits, temperature=1.0):
    scaled = logits / temperature
    return softmax(scaled)

# temperature < 1 → 分布更尖，較常選高機率 token
# temperature > 1 → 分布更平，低機率 token 機會增加
面試連回工程：需要 structured tool call / deterministic classification 時，通常偏低 randomness；creative generation 才可能接受更高多樣性。
Q：為什麼把更多文件塞進 context，不一定更準？

因為更多 context 同時帶來更多噪音、衝突資訊與 attention 競爭；也增加 lost-in-the-middle、latency 與 cost。RAG 的目標不是最大 context，而是最高 quality / relevance 的 context。

7.11 Code：Timeout / Retry 要有邊界

簡化版 timeout + exponential backoff
import asyncio

async def call_with_retry(fn, attempts=3):
    for i in range(attempts):
        try:
            return await asyncio.wait_for(fn(), timeout=2.0)
        except (TimeoutError, ConnectionError):
            if i == attempts - 1:
                raise
            await asyncio.sleep(0.2 * (2 ** i))

注意：不是所有錯誤都 retry。400 類 input error、權限錯誤通常重試沒意義；有副作用的 tool 還要考慮 idempotency。

8. 模擬面試題庫

RAG｜為什麼 Hybrid Search 常比純 Vector Search 穩？

因為企業資料同時有語意查詢與 exact-match 需求。Dense 擅長語意，BM25 擅長錯誤碼、型號、專有名詞；Hybrid 能互補。回答時再補融合方法（如 RRF）與 eval 方式。

RAG｜Top-K 要設多少？

不是固定答案。K 越大 recall 可能上升，但 context precision、cost、latency 可能惡化。應以 retrieval metric + downstream answer quality 找 operating point；常搭配「大 K retrieve，小 K rerank」。

Agent｜你會怎麼防止 tool 被重複執行？

對有副作用的操作使用 idempotency key、transaction / unique operation ID；agent state 記錄已執行 action；必要時由 deterministic workflow 控制 transition，而不是只靠 prompt。

Agent｜Supervisor multi-agent 有什麼缺點？

多一層 routing latency、token cost、共享狀態一致性、錯誤歸因困難、evaluation 複雜。若 worker 邊界不清楚，很可能只是「角色扮演式拆分」。

LLM｜KV Cache 解決什麼？

自回歸解碼時避免每一步重算所有舊 token 的 K/V，使 generation 更快；代價是佔 GPU memory，context 與 batch 越大越明顯。

LLM｜RAG 和 Fine-tuning 的差別？

RAG 解「知識外部化、可更新、可引用」；fine-tuning 更適合改模型行為、風格、task pattern。若知識常變，不應把它硬塞進模型權重。

Evaluation｜LLM-as-a-Judge 可以相信嗎？

不能盲信。它適合大規模語意評估，但要用明確 rubric、固定 judge、human calibration、pairwise / consistency checks；高風險指標不能只靠 judge。

Evaluation｜為什麼只看 user thumbs-up 不夠？

稀疏、有 selection bias，而且無法定位問題在 retrieval、agent 還是 generation。它適合當 online signal，不適合取代 offline diagnostic metrics。

System Design｜要不要用 Kubernetes？

先看 deployment scale、availability、team ops 能力與 service complexity。K8s 是手段，不是答案。小規模服務可能 managed container platform 更簡單。

System Design｜如何控制 LLM 成本？

model routing、小模型處理簡單任務、減少 context、cache、batch、限制 agent steps、結構化 tool result、offline async tasks；同時用 quality metric 確認不是只省錢卻掉品質。
